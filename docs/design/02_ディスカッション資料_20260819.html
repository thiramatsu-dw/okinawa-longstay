2. 確定した構成方針(3原則)

原則 一

Kintone はマスタとして活用

客室・オーナー・顧客・入退去履歴など、利用中12アプリをデータの正として維持・整備する

原則 二

Excel・外部帳票は Google 基盤へ集約

予約表・清掃計画表・相殺リスト・MR の Excel 4種を Google の仕組みに置き換える

原則 三

Kintone API で相互連携

Kintone REST API と Google API を同期ジョブでつなぎ、二重入力と突き合わせ作業をなくす

6. 本日の論点

赤のタグは本日決めたい判断、青のタグは事実確認・方向づけができれば十分なもの。

論点 1

予約表の実装形態

本日決めたい

Phase 1 の中核。126室×31日のマトリクスをどう作るかで開発スピードと操作性のバランスが変わる。

A. スプレッドシート+GAS で先行
最速で移行でき、現場が慣れた操作感。空室検索・Kintone 連携は GAS で実装。行列の固まった見た目に限界が来たら B へ発展させる
B. 最初から専用 Web アプリ
ドラッグ操作・色分け・フィルタなど操作性は最も高いが、初期開発が大きく、現場に届くまでが遅い

決めたいこと: A で開始してよいか。あわせて Phase 1 のプロトタイプを今回の訪問期間中に作り始めることの合意。

論点 2

「見積もりくん」の稼働実態

事実確認

システム一覧では「利用中」、ヒアリングメモでは「まだ稼働していない」と記述が割れている。料金・保証金マスタの品質は高く、拡張土台としての期待値が大きい。

確認したいこと: 現在の利用実態と、マスタ(部屋・シーズン料金・保証金ルール)が最新かどうか。

論点 3

MR 業務委託(田中さん)の今後の役割

方向づけ

MR 自動生成後、レポート「作成」の作業はなくなる。委託の位置づけを決めておかないと移行計画が引けない。

A. 確認・検収役へ移行
自動生成された MR・請求書のチェックを担ってもらい、品質の連続性を保つ
B. 社内へ巻き取り
確認作業も社内で行い、委託を段階的に終了する

決めたいこと: どちらの方向で移行計画を作るか(即決不要、方向感だけでも)。

論点 4

サイボウズ スケジュールの位置づけ

方向づけ

入退去の立ち会い・清掃予定を予約表からサイボウズへ手で転記している。新予約表ができると転記の意味が変わる。

A. 新予約表から自動連携
運用は現状のままサイボウズを見る。転記だけを自動化する(移行の負担が最小)
B. Google カレンダーへ移行
Google 基盤へ寄せて一元化。ただし現場の慣れの切り替えコストが発生

決めたいこと: Phase 1〜2 の間は A(自動転記)でよいか。

論点 5

データの正と同期ルール

設計合意

「どのデータはどちらが正か」を決めないと、同期が双方向になり事故のもとになる。

案: 役割で正を分ける
マスタ(客室・オーナー・顧客)は Kintone が正 → Google へ配信。予約・滞在予定は Google 予約表が正 → 確定・完了時に Kintone 履歴へ書き戻し。日次同期+必要時の手動実行
確認ポイント
リアルタイム性が必要な場面(ダブルブッキング防止など)がどこまであるか。案内中ステータスの運用ルール

決めたいこと: この正の置き方で設計を進めてよいか。

論点 6

アカウント・権限の準備

事務・準備

開発と連携に必要な環境の整備。7月会議で合意済みの開発用 Mac・Splashtop・Claude アカウントに加えて必要なもの。

確認したいこと: Kintone API トークンの発行(対象アプリと権限範囲)、作業用 Google Workspace アカウント、予約表・清掃計画の共有ドライブの置き場所。

解消済みの論点: 「MR の元データの所在」→ 予約表から関数で作成し Kintone には非保管(ヒアリング資料で判明)。「物件情報アプリの役割」→ 新規オーナー契約時に客室情報・オーナー情報とあわせて登録して使用。

7. 本日のゴールと次のステップ

  • 決定: 論点1(予約表はスプレッドシート+GAS で先行)と Phase 1 着手の合意
  • 方向づけ: 論点3〜5(委託の役割・サイボウズ連携・データの正)
  • 確認: 論点2(見積もりくん)・論点6(アカウント準備)
